# Phase 1.5: Generalise the core

**Date:** 2026-10-24
**Status:** Approved 2026-10-24, in progress (steps 1, 2, 2b, and 3 done; step 4 next)
**Plan:** [`2026-10-24-exe-parity-plan.md`](../plans/2026-10-24-exe-parity-plan.md), Phase 1.5
**Builds on:** [`2026-10-24-phase1-data-driven-content.md`](2026-10-24-phase1-data-driven-content.md)

## Goal

Four assumptions in `sim` would make every later phase more expensive: a
replay format with no version, a single resource, exactly two players, and a
closed list of unit and building kinds. This phase removes all four without
adding gameplay. A default game plays the same as before, apart from the
replay format.

## Reference note

- `FUN_0040bdf0` creates the world in stages and logs each one: "World: new
  game", "after_new_map", "after_gaia", "after_players". The player count is
  read from the game settings, `*(short *)(param_2 + 0x294) + 1` including
  Gaia, and the players are created through the vtable call at `+0x68`. Gaia
  is player 0; players 1 to 8 follow.
- The `while (iVar6 < 9)` loops in the same function are **not** player
  creation. They pair players on the same team (`FUN_005eb0f0` reads a team
  number per slot) and set diplomatic stances (`FUN_00556870`). Teams and
  diplomacy are therefore fixed when the world is created; Phase 10 builds on
  that. This phase keeps a per-player defeated flag so that Phase 10 only
  changes how the outcome is derived.
- The original tracks defeat per player: "Defeated", resign, and
  `DropDeadPlayer`.
- Resources are entries 0 to 3 of a per-player attribute table: a float array
  at `player + 0xa8`, length at `player + 0xa4`, read and written by
  `FUN_00555510`, `FUN_00555380`, and `FUN_00555440`, which special-case
  indices 0 to 3. Later entries hold population headroom, housing, and other
  values that technologies change by index ("aqquire %d of attribute %d").
- In the original, mines, sheep, deer, and relics belong to Gaia.
- The original's data (`data/empires2_x1_p1.dat`) holds unit types in tables
  indexed by ID, not by name.

## Step 1: Replay format version

**Why first:** this phase changes the replay format twice (player IDs and
kind IDs). Old replays must fail with a clear message, not a confusing parse
error or a desync.

- `Replay` gains `version: u32`. `Replay::FORMAT_VERSION` is the version this
  build writes and reads. This phase sets it to `2`; a file with no `version`
  field is version `1` (everything before this phase).
- `app::load` reads the version before anything else, with a small struct that
  has only that field. A different version returns
  `ReplayError::Version { found, expected }`, displayed as
  `replay is format version 1; this build plays version 2`.
- This replaces the deferred finding that the old-format replay test only
  proved parsing. The Phase 1 test that loads an old replay with default
  content becomes a test that an old replay is refused by version.
- Also fixes the deferred finding that a bad `--content` file blocks `--play`:
  `main` skips loading `--content` when `--play` is given.

**Tests:** a replay written by this build reads back; a version-1 file is
refused with both versions in the error; a file with a future version is
refused the same way; `--play` with a broken `--content` file is not
stopped by the content (unit test on the option handling, which moves into a
testable function in `app`).

## Step 2: Resources as a per-player array

**Why:** Phase 2 adds food, wood, and stone. Doing the type change here keeps
Phase 2 about gameplay.

- `pub enum Resource { Food, Wood, Gold, Stone }`, a closed enum. The original
  keeps the four stock resources as the first four entries of a larger
  per-player attribute table (see the reference note). This phase models only
  those four. Other attributes arrive with the phases that use them:
  population cost and headroom in Phase 3, technology changes by attribute
  index in Phase 4. Adding them is additive and does not change `Resources`.
- **Mapping for the Phase 1.6 converter**, recorded here so it is not
  rediscovered:
  - Attribute index order in the original is food 0, wood 1, **stone 2,
    gold 3**. Our `Resource::ALL` order is food, wood, **gold, stone**. The
    converter maps by name, never by position.
  - The original stores amounts as `float`; we store `i32`. The converter
    rounds to the nearest integer and reports any value that was not already
    whole.
  - A `.dat` unit cost is up to three (attribute, amount) entries. Attribute
    4 is population; it is ignored until Phase 3 adds a population cost.
- `pub struct Resources { food, wood, gold, stone }` of `i32`, with indexing by
  `Resource`, `can_afford`, and saturating add and subtract.
- `Player { resources: Resources }` replaces `Player { gold }`.
- `UnitStats::cost: Resources`. In RON, `cost: (gold: 50)`, with missing
  resources defaulting to zero. Validation: no part may be negative.
- `MapSpec::with_starting_resources(Resources)`. `with_starting_gold` stays as a
  shorthand.
- `WorldView::resources(player)`. `gold(player)` stays as a shorthand, so most
  tests do not change.
- Gathering still produces gold only; Phase 2 generalises it. The checksum
  hashes all four resources.

**Tests:** training charges every part of a mixed cost; training is refused if
any one resource is short; a cost with a negative part fails validation; a
missing resource in RON reads as zero.

## Step 2b: Widen the checksum

**Why:** this phase is already a replay break, so widening the checksum now
costs no extra version. It also catches Step 4 mistakes: if a kind ID resolves
to the wrong entry, a checksum that hashes kinds diverges at the next sample
instead of whenever HP or position happens to differ. Phase 13 wanted this
before multiplayer anyway.

- Add to `World::checksum`: unit kind; unit order, including its target and
  gather phase; mine ticks; attack cooldown; building kind, owner, queue
  contents, and training ticks left.
- Not hashed: routes and stuck counters (path-planning detail that follows
  from the order and position), the flow field cache, and the path queue.

**Tests:** for each added field, two worlds that differ only in that field have
different checksums.

## Step 3: Up to 8 players plus Gaia

**Why:** AI opponents, free-for-all, teams, and multiplayer all need more
than two players, and Gaia owns the map's neutral objects.

- `PlayerId(u8)`, with `PlayerId::GAIA = 0` and players `1..=8`. Constants
  `PlayerId::ONE` and `PlayerId::TWO` keep tests readable. `index()` returns
  the slot in the player array. `other()` is removed.
- `MapSpec::with_players(n)` for `n` in `2..=8`; default 2. A map that places
  an entity for a player beyond `n` is rejected by `World::with_content`'s
  caller (`MapSpec::validate`), not silently clamped.
- `World` keeps `players: Vec<Player>`, slot 0 for Gaia.
- Gaia cannot issue commands (dropped like any invalid command), never loses,
  and never wins. Mines stay ownerless entities in this phase; Phase 2 turns
  them into Gaia-owned resource sites.
- Each `Player` has a `defeated: bool`. A player is defeated when they have no
  buildings; this "no buildings" rule is the PoC's and is **provisional**,
  since the original's conquest rule may differ. Once set, `defeated` never
  clears. A defeated player's commands are dropped.
- The outcome is derived from those flags, not stored on its own:
  `enum Outcome { Won(PlayerId), Draw }`. When exactly one non-Gaia player is
  undefeated, they win. When the last undefeated players are all defeated on
  the same tick, it is a draw. Phase 10 changes only this derivation, to
  teams. Resigning and dropped connections will set the same flag.
- `WorldView::defeated(player)` exposes the flag.
- App: Tab cycles through players `1..=n`. Eight player colours. The overlay
  prints `player 3` from the ID rather than a match on two variants.

**Tests:** a 4-player map plays to one winner after three players lose their
buildings; a player with no buildings is defeated while the others play on,
and their commands are dropped; two players losing their last building on the same tick, leaving
none, is a draw; a command stamped with Gaia is dropped; a map with a building
for player 5 of 4 fails `MapSpec::validate`; the determinism and replay
property tests run on a 3-player map as well as a 2-player map; Tab cycles
1 → 2 → 3 → 1 on a 3-player map.

## Step 4: Content keyed by ID

**Why:** adding a unit or building type should be a RON entry, not a code
change. Phase 2 already needs new buildings.

- `UnitKind(u16)` and `BuildingKind(u16)` become indices into
  `Content::units: Vec<UnitStats>` and `Content::buildings: Vec<BuildingStats>`.
  A lookup is a direct index, as cheap as today's `match`.
- Each entry gains a `name: String`, unique within its table. RON refers to
  other entries by name (`trains: ["villager"]`); the loader resolves names to
  IDs and reports an unknown name as an error naming the field.
- `sim` code never names a specific kind. Behaviour that used to test
  `kind == UnitKind::Villager` comes from a flag on the entry:
  `UnitStats::gathers: bool` (may take a gather order and carries a load).
  The app's hotkeys train the first and second entry of the building's
  `trains` list instead of naming villager and soldier.
- Building footprint `size` moves into `BuildingStats`, because a building ID
  can no longer be matched on. `MapSpec::home` and the app's picking and
  drawing read it from content.
- `MapSpec::proof_of_concept(&Content)` looks its kinds up by name and returns
  an error if the content lacks `town_center`, `barracks`, or `villager`.
  `Content::unit_named` and `Content::building_named` do the lookups.
- Validation adds: names unique and non-empty; every `trains` entry resolves;
  at least one unit type.
- **Each entry names its sprite** (added after the pre-stage made drawing
  required): `UnitStats::graphic` and `BuildingStats::graphic`, a sprite ID
  in `graphics.drs`, as the original's `.dat` gives each unit a standing
  graphic. The app's sprite table and picking bodies become keyed by kind ID
  and are built from these, so a unit type added only in RON is drawn with
  the sprite its entry names. A graphic ID the install does not hold is a
  startup error naming the entry.

**Tests:** a unit type added only in RON (an archer) can be trained at a
building whose `trains` lists it, and it fights with its own numbers; a unit
type without `gathers` refuses a gather order; an unknown name in `trains` is
an error naming the field; a duplicate name is an error; a building's footprint
comes from content; the proof-of-concept map fails cleanly on content without
a town centre.

## Performance

Lookups stay direct indices. The tick benchmark (`crates/sim/benches/step.rs`)
is re-run at the end of the phase and recorded in `docs/benchmarks.md`. Load
time for large tables is measured in Phase 1.6, once real `.dat`-sized
tables exist.

## Replay

This phase is a replay break, recorded here: the cost shape, player IDs, kind
IDs, and the checksum all change. Version-1 replays are refused with a version
error.

Steps 1 to 3 were committed (at the user's request) under format version 2,
before step 4 changes `Content` and `MapSpec` again. So that no version number
ever means two layouts, step 4 sets `Replay::FORMAT_VERSION` to **3**, and
version-2 files are refused by version like version-1 files.

Version 3 is final only when the phase ends.

## Gate

1. A 4-player map plays to a single winner.
2. A unit type added only in RON can be trained and fights.
3. An old-format replay is refused with an error naming both versions.
4. `cargo test --workspace` and `cargo clippy --workspace --all-targets` pass,
   and the tick benchmark stays under 5 ms.
5. Code review and direction check (plan guideline 10).
