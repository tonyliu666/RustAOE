# Phase 1.6: `.dat` converter

**Date:** 2026-10-25
**Status:** Approved 2026-10-25, in progress (steps 1, 2, 3a, and 3b done)
**Plan:** [`2026-10-24-exe-parity-plan.md`](../plans/2026-10-24-exe-parity-plan.md), Phase 1.6 and its notes
**Builds on:** [`2026-10-24-phase1.5-generalise-core.md`](2026-10-24-phase1.5-generalise-core.md) (content keyed by ID, the mapping notes)

## Goal

Take game numbers from the original's data instead of from memory. A dev tool
reads `data/empires2_x1_p1.dat` from the user's install and writes our RON
content format. The game itself keeps reading only RON; it never opens a
`.dat`, and nothing from the `.dat` is committed.

This phase builds and proves the tool. It does **not** change the numbers the
game plays with: `default.ron` keeps today's values, so no replay breaks here.
Phase 2 adopts converted values (the villager's food cost first).

## Reference note

- `FUN_00586b20` names the `.dat` path (`data\empires2_x1_p1.dat`).
- The file is raw deflate data (zlib's format without its header). Decompressed,
  it starts with a version string; The Conquerors writes `VER 5.7`.
- The layout is not in the binary as data; the community has documented it
  (openage's format description and genieutils, both reading this exact file).
  We follow those descriptions section by section and check every section
  against the real file (below). No code is copied from them.

## What is read

Only what our content has fields for, and what is needed to reach it. In file
order, the reader passes over: terrain restrictions, player colours, sounds,
**graphics**, terrains and borders, random-map data, technology effects, then
reads the **civilisations and their units**. Sections after the units (research,
tech tree) are left for Phase 4.

Per unit, the fields that map to content:

| `.dat` field | Our field | Conversion |
| --- | --- | --- |
| Name, unit ID | `name` | Lower-case with `_` for spaces; the original ID is written beside the entry as a RON comment |
| Hit points | `max_hp` | As is |
| Speed (tiles per second, float) | `speed` (tiles per tick, `Fx`) | Divide by 20, round to the nearest 1/65536 |
| Attacks (class, amount) | `damage` | Sum of the base melee or pierce amount; armour classes wait for Phase 6 |
| Max range (tiles, float) | `range` | To `Fx`, nearest |
| Reload time (seconds, float) | `attack_cooldown` (ticks) | Times 20, round half up, at least 1 when the unit attacks |
| Collision size x (tiles, float) | `radius` | To `Fx`, nearest |
| Cost (up to three of attribute, amount, used) | `cost` | Attributes 0 to 3 map **by name**: food 0, wood 1, **stone 2, gold 3** (our order is food, wood, gold, stone). Attribute 4, population, is ignored until Phase 3 |
| Train time (seconds) | `train_ticks` | Times 20, round half up, at least 1 |
| Standing graphic | `sprite` | The graphic's entry in the `.dat` graphics table names an SLP; that SLP ID is `sprite`. Extra pieces ("deltas", why the town centre is drawn in parts) are recorded in the converter's report but not drawn yet |
| Task list contains a gather task | `gathers` | True if any task gathers a resource |

Per building, also: `size` from the building's footprint (collision size x
times 2, rounded), `drop_off` from its resource drop-site flags, and `trains`
from each unit's train location (the building that trains it).

Rounding rule, everywhere: nearest representable value, halves away from zero;
the converter's report lists every value that was not already whole in our
units, so nothing is rounded silently.

## Type IDs

Our `UnitKind` and `BuildingKind` stay **compact positions** in our lists. The
original's unit ID is written as a RON comment beside each entry, for tracing
and for tests. Adding it as a content field would change `Content`'s shape,
which is a replay break; it can come later with a version bump if a feature
needs it at run time.

## Which units

By default the converter writes the four types the game has today
(villager, militia as our soldier, town centre, barracks), found by original
ID. `--all` writes every unit and building of one civilisation (Britons by
default, `--civ N` to choose), for the performance checkpoint and later
phases.

## Archives and sprite loading

Also in this phase, because a converted table makes the current loader too
slow and because converted `sprite` IDs can sit in several archives:

- **Confirm the archive order** from the disassembly: the pushes before the
  eight `FUN_00543370` calls in `FUN_0043ae90`. The decompile lost the names;
  the evidence so far says the three expansion archives come first.
- **Ordered, parse-once archive search** in the app: parse each archive once
  at startup, keep them in the confirmed order, and look a sprite up by type
  and ID in the first archive that has it.
- **Load time:** measure `load_images` with the default content and with an
  `--all` table. If the full table is over 2 seconds, decode each type's sprite
  on first use instead of at startup.

## Crate layout

- `assets::dat`: the `.dat` reader, pure parsing over bytes like the other
  readers, returning plain structs. Errors are values.
- `crates/datconv`: a small binary, a workspace member, that reads the file,
  maps it with the table above, and writes RON in `app`'s content format.
- One new dependency: a pure-Rust deflate decoder (`miniz_oxide`) for the
  decompression. Std has none.

## Steps

1. **Archive order.** Read the pushes in the disassembly; record the order.
   Then the ordered, parse-once search, with a fake-install test that a sprite
   in two archives resolves to the first archive's copy.
2. **Decompress and header.** Tests: compressed bytes built in the test
   inflate back; a wrong version string is an error.
3. **Walk to the units.** One reader per section, each tested with bytes built
   in the test. On the real file, every section must end where the next one
   begins (checked by an ignored test that runs when `AOE_ASSETS` is set).
4. **Units and graphics.** Read the fields in the table, resolve standing
   graphics to SLP IDs.
5. **Convert.** The mapping and rounding rules, each tested on its own;
   `datconv` writes RON; the output parses with `app::parse_content` and
   passes `validate`.
6. **Performance checkpoint.** Record `load_images` time for default and
   `--all` content in `docs/benchmarks.md`; make loading lazy if needed.

## Gate

1. `cargo run -p datconv -- --install DIR --out FILE.ron` writes content that
   loads and validates.
2. Known values, checked by the ignored real-file test and recorded here:
   the villager has 25 hit points, costs 50 food, and trains in 25 seconds
   (500 ticks); the militia costs 60 food and 20 gold. The exact figures the
   tool reads are written into this spec when the step runs, not assumed.
3. Every conversion rule has a test with bytes or values built in the test.
4. A sprite ID present in two archives resolves the way the original does.
5. `load_images` times recorded; tick benchmark unchanged.
6. `cargo test --workspace` and clippy pass without an install (real-file
   tests are ignored unless `AOE_ASSETS` is set). No game data committed.

## Step 1 result (2026-10-25)

**Archive order, confirmed from the disassembly.** The eight calls to
`FUN_00543370` in `FUN_0043ae90` push these file names (read from `.data` at
the pushed addresses), each with the archive type `"tribe"`:

| Order | Call | Pushed address | Archive |
| --- | --- | --- | --- |
| 1 | `0x43af73` | `0x66f634` | `sounds_x1.drs` |
| 2 | `0x43af8d` | `0x66f624` | `gamedata_x1.drs` |
| 3 | `0x43afa8` | `0x66f610` | `gamedata_x1_p1.drs` |
| | | | (then `LoadLibraryA("language_x1_p1.dll")`) |
| 4 | `0x43b063` | `0x66eec4` | `sounds.drs` |
| 5 | `0x43b07d` | `0x66eeb4` | `graphics.drs` |
| 6 | `0x43b097` | `0x66eea8` | `terrain.drs` |
| 7 | `0x43b0b0` | `0x66ee98` | `interfac.drs` |
| 8 | `0x43b0cd` | `0x66ee88` | `gamedata.drs` |

`FUN_00543370` appends each archive to the tail of the list at `DAT_006b59e4`,
and `FUN_00543630` walks it from the head, so the first archive opened wins:
the expansion's archives override the base game's.

**Ordered, parse-once search** (`app::sprites::Archives`): every archive is
read and indexed once (`assets::Drs::entries`), and a file is found by type
and ID in the first archive, in the order above, that has it. `interfac`,
`graphics`, and `terrain` are required; the others are used where present.
Tests: an expansion copy overrides `graphics.drs`; a sound sharing a
sprite's ID does not hide the sprite (the real install has such IDs, 5110
for one). Each was also checked by breaking the rule on purpose.

`load_images` with the default content on the real install: 145 ms (release
build), the baseline for step 6.

## Step 2 result (2026-10-25)

`assets::dat::decompress` inflates the raw deflate stream (`miniz_oxide`) up
to `MAX_DECOMPRESSED` (256 MB), so a file that inflates without end stops
with an error instead of exhausting memory. `assets::dat::version` reads the
8-byte version string and accepts only `VER 5.7`.

On the real install (ignored test, run with `AOE_ASSETS` set and
`--ignored`): `empires2_x1_p1.dat` is 1,041,720 bytes compressed and
5,649,567 bytes inflated, version `VER 5.7`.

## Step 3a result (2026-10-25)

**Layout source.** The genieutils project's readers for this file
(`github.com/Tapsa/genieutils`, `src/dat/*.cpp`, `include/genie/Types.h`),
read for field layouts only, with every version condition resolved for
`GV_TC` (The Conquerors sits after `GV_T8` and `GV_AoKE3`, before `GV_C2` and
`GV_SWGB`). No code was copied.

**Sections read** (`assets::dat::Dat::parse`), in file order:

| Section | Layout for The Conquerors |
| --- | --- |
| Header | 8-byte version string |
| Terrain restrictions | `i16` restriction count, `i16` terrain count, two `i32` pointer tables, then per restriction a `f32` per terrain and a 16-byte pass graphic per terrain |
| Player colours | `i16` count, nine `i32` each |
| Sounds | `i16` count; per sound `i16` ID, `i16` delay, `i16` file count, `i32` cache time, then 23 bytes per file (13-byte name, `i32` resource, `i16` probability, civilisation, icon set) |
| Graphics | `i16` slot count, an `i32` pointer per slot, then a graphic for each non-zero pointer: 21-byte name, 13-byte file name, `i32` SLP, flags and coordinates (14 bytes), `i16` delta count, `i16` sound, `u8` angle-sounds flag, `i16` frames, `i16` angles, three `f32`, `u8` sequence type, `i16` ID, two `u8`, then 16 bytes per delta and, when flagged, 12 bytes per angle |

**Checked on the real file:** 22 terrain restrictions over 41 terrains,
15 player colours, 506 sounds, 7,367 graphic slots of which 7,014 hold a
graphic, every one storing its own index as its ID; the graphics end at
byte 917,004, where the terrain block begins.

**The sprites chosen by eye in the pre-stage, found in the `.dat`:** barracks
SLP 131 is graphic 91 `BRKS2NNF`; town centre SLP 901 is graphic 445
`RTWC2NNF`; tree SLP 1270 is graphic 1671 `TREEJ_NN`; gold mine SLP 4479 is
graphic 4359 `GOLDM_N0`. Two were not what they seemed: SLP 1181, used for the
soldier, is graphic 1154 `THSWD_FN`, the two-handed swordsman standing, not the
militia; SLP 1473, used for the villager, is graphic 1278 `VMBAS_AN`, a male
villager's attack animation, not its standing pose. Step 4 takes each unit's
real standing graphic from its `.dat` entry.

## Step 3b result (2026-10-25)

`Dat::parse` walks on from the graphics table to the civilisations, with
every condition in genieutils' readers resolved for `GV_TC`:

| Section | Layout for The Conquerors |
| --- | --- |
| Terrain block | No counts: a fixed 42,208 bytes. Map fields (24 bytes), 19 tile sizes of three `i16`, an `i16` of padding, 42 terrains of 436 bytes, 16 borders of 1,440, a map row offset, six `f32` map bounds, 14 `i16` tile and block fields, two pointers and three flag bytes, then 21 bytes and 157 `i32` the game fills in at run time. A terrain's and a border's animation fields are 23 bytes |
| Random maps | `i32` count, pointer, a 72-byte header per map (ID, nine fields, each list's count and pointer), then each map again without its ID and with its lists: lands 44 bytes, terrains 24, units 44, elevations 24. The two copies must agree on every list's length |
| Effects | `i32` count; per effect a 31-byte name and an `i16` command count, 11 bytes a command (type, three `i16`, an `f32`) |
| Unit headers | `i32` count; per unit ID a flag and, when it exists, an `i16` task count and 59 bytes a task |
| Civilisations | `i16` count, where the reader stops for now |

**Checked on the real file:** the first terrain is `Grass` (`g_grs`), the
second `Water`; the random maps begin at byte 959,212, exactly 42,208 after
the terrain block, and there are 9; 514 effects, every one named `CHUN4` in
this file (the names carry nothing; the command counts vary as they should);
866 unit headers of which 842 exist; 19 civilisations at byte 1,092,830, the
first named `Gaia`. The other 18 names need each civilisation's units walked,
which is step 4.

Counts are not trusted for allocation: lists grow as entries are read, so a
damaged count runs out of file (`Truncated`), not memory.
